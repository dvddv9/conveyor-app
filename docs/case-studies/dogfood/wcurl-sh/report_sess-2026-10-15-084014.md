# Dependabot Configuration Review — dependabot.yml

[ECHO] Ревью `dependabot.yml` (schema v2, ~40 строк): 2 экосистемы (github-actions, pip), quarterly-интервал, cooldown 30/7/15/7/3 дней, группы `patterns: '*'`. Task type: compliance. Уровень D1.

[ROUTE] stage0 → stage1 (scanner) → stage2 (analyst) → stage4 (synthesizer) → stage5 (transmitter). Research: web_search использован (1 запрос). Substitution: не обнаружена.

[CONCLUSION] Конфиг синтаксически корректен и следует схеме Dependabot v2, но как supply-chain политика недонастроен: quarterly-интервал для github-actions даёт окно CVE до ~120 дней, группа `patterns: '*'` укрупняет diff и риск, отсутствует `insecure-external-code-execution: deny` для pip (потенциальный RCE в CI), не заданы `open-pull-requests-limit`, `allow`, `ignore`, `labels`, `reviewers`. Приоритет — закрыть RCE-вектор и сократить окно экспозиции. Признаков наличия секретов в CI-job с pip install не найдено (VERIFY: не проверялось).

[RISK_NODES]
- **RN-1 (важно):** `directory: .github/workflows` для pip — если requirements/constraints вынесены в корень или подкаталоги, pip-обновления молча не сработают.
- **RN-2 (важно):** `groups.patterns: '*'` смешивает major/minor/patch и разные пакеты в один PR — крупнозернистый ревью и откат.
- **RN-6 (важно):** отсутствуют `allow`/`ignore`/`open-pull-requests-limit`/`labels`/`reviewers` — нет управления потоком и владельца.
- **RN-8 (важно):** нет явного `open-pull-requests-limit` — PR-шторм или молчаливое усечение дефолтным лимитом.
- **RN-11 (важно):** pip-группа может принести major-бампы в одном PR; `semver-major-days: 15` задерживает, но не блокирует.
- **RN-3, RN-4, RN-5, RN-7, RN-9, RN-10 (опционально):** дублирование с Renovate, неполнота относительно reference-URL, различие cooldown без обоснования, накопление отставания, отсутствие шаблонизации, косвенные конфликты в lock-файлах.

[PLAN_B]
- SEC-1: сократить интервал для github-actions до monthly/weekly, сохранив cooldown как защиту от свежих регрессий.
- SEC-2: явно задать `insecure-external-code-execution: deny` для pip-экосистемы.
- SEC-3: добавить `registries` при наличии приватных индексов.
- RN-1: проверить фактическое расположение requirements/constraints и скорректировать `directory`.
- RN-2: разбить `groups.patterns: '*'` на подгруппы (major/minor/patch или по назначению).
- RN-6: добавить `allow`/`ignore`/`open-pull-requests-limit`/`labels`/`reviewers`.
- RN-8: задать `open-pull-requests-limit` явно.
- RN-11: пинить GitHub Actions по SHA и требовать ручное ревью major-бампов.
- FP-1: включить hash-pinning и trusted publishers для pip; ограничить `GITHUB_TOKEN` permissions.
- FP-4: ввести SLO «критический CVE → PR в течение N дней» и алерт на пропущенные обновления.

[THREAT_MODEL]
- **Компоненты:** dependabot.yml, Dependabot service, github-actions ecosystem, pip ecosystem (.github/workflows), CI/CD pipeline.
- **Trust boundaries:** Dependabot service → репозиторий (PR-канал); внешние реестры (PyPI, Marketplace) → CI; CI workflow → секреты/окружение.
- **Threats (STRIDE):**
  - **T (Tampering) — критично:** компрометация PyPI-пакета (typosquatting / account takeover) → Dependabot приносит вредоносную версию как «обновление».
  - **E (Elevation of Privilege) — критично:** обновление стороннего action до версии с изменённым поведением → исполнение произвольного кода в CI с доступом к секретам.
  - **S (Spoofing) — важно:** подмена источника обновления / PR от имени Dependabot при компрометации аккаунта или webhook.
  - **I (Information Disclosure) — важно:** утечка секретов CI через build-хуки пакета при `insecure-external-code-execution`.
  - **D (Denial of Service) — важно:** PR-шторм при срабатывании группы `'*'` без `open-pull-requests-limit`.
  - **R (Repudiation) — опционально:** отсутствие labels/reviewers/assignees — нет владельца обновлений.
- **Итого:** 6 threats (2 критично, 3 важно, 1 опционально).

[SILENCE_LAYERS]
- **Input silence:** нет данных о числе зависимостей, частоте релизов, размере репозитория, наличии приватных реестров → невозможно оценить адекватность quarterly-интервала и лимита PR.
- **Assumption silence:** предполагается, что все pip-зависимости лежат в `.github/workflows` и Dependabot их найдёт; `directory` задан жёстко без проверки.
- **Consequence silence:** молчаливый пропуск обновлений (лимит PR, неверный directory) или крупный ломающий PR из группы `'*'`; компрометация через supply-chain может быть необратимой.

[INTERSECTION_RISKS]
- **input_silence × assumption_silence:** нет данных о числе зависимостей × жёсткий `directory` для pip → Dependabot может не находить pip-зависимости вовсе, команда считает, что обновления работают (ложное чувство покрытия).
- **assumption_silence × consequence_silence:** группа `'*'` × отсутствие allow/ignore × CI-секреты → один крупный PR с major-бампами и потенциально вредоносным пакетом проходит в CI с секретами (supply-chain RCE).
- **input_silence × consequence_silence:** quarterly-интервал × неизвестная частота CVE → окно экспозиции к критическим CVE может достигать месяцев без видимого сигнала.

[ASSEMBLY] Конфиг — декларативная политика обновления зависимостей. Иерархия: core (dependabot.yml) → service (Dependabot service, CI/CD pipeline, github-actions, pip) → infra (Marketplace, PyPI, branch protection, секреты CI). Критический путь: PyPI/Marketplace → Dependabot PR → CI pipeline → secrets. Циклов нет.

[REFACTORING] Три опции:
- **Option A — Minimal hardening (1–2 дня):** добавить `insecure-external-code-execution: deny`, `open-pull-requests-limit`, `labels`/`reviewers`; gha-интервал → monthly. Закрывает SEC-2 и RN-8, не решает RN-2 и RN-1.
- **Option B — Structured policy (3–5 дней):** A + разбиение groups на major/minor/patch или по назначению + `allow`/`ignore`. Решает RN-2, RN-6, RN-8, RN-11. Больше PR — выше нагрузка на ревью.
- **Option C — Full supply-chain posture (5–8 дней):** B + hash-pinning pip, pin actions по SHA, SLO «критический CVE → PR за N дней», алерты, branch protection. Закрывает FP-1 на уровне политики.

[PARALLELS] Renovate как альтернатива Dependabot — даёт более гранулярный контроль (отклонён без анализа в stage4, отмечено в COVE). Hash-pinning + trusted publishers закрывают supply-chain вектор параллельно с `deny`. Cooldown выполняет роль тормоза от свежих регрессий — параллель с circuit breaker.

[TESTS] Классические тесты не применимы к декларативному конфигу. Возможна валидация схемы: `actionlint` / dependabot schema check в CI. Dry-run: убедиться, что Dependabot находит pip-зависимости. Проверить, что `insecure-external-code-execution: deny` не ломает легитимные build-хуки.
