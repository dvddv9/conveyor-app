# RequestFilter.java — Code Review (D3)

[ECHO] Sakai `RequestFilter` (servlet filter, ~500+ строк, слайс обрезан до полей/констант). Единая точка входа всех запросов Sakai: session resolution, upload parsing, encoding, cluster redirect, cookie emission, principal check. Method bodies вне слайса.

[ROUTE] stage4 (synthesizer) → stage3 (assembler). task_type=review → обязательны [RISK_NODES], [PLAN_B], [TESTS], [MATRIX].

[CONCLUSION] God-filter с 4 критичными рисками: thread-local leak при исключении в `chain.doFilter` (RN-1/FP-1), session fixation через `session.parameter.allow` (SEC-1), DoS через upload (SEC-4), блокировка всех запросов при недоступности ClusterService (RN-8/FP-2). Признаков автоматического cleanup ThreadLocalManager не найдено (VERIFY: cleanup-путь вне слайса). Признаков значения `session.parameter.allow` в проде не найдено (VERIFY: конфиг не проверен). Рекомендация: Option A (hardening in place, 3–5 дней) как первый шаг.

[RISK_NODES]
- RN-1 (критично): thread-local leak при исключении в `chain.doFilter` — cleanup-путь не виден (VERIFY).
- RN-8 (критично): ClusterService недоступен → блокировка всех запросов вместо graceful degradation.
- RN-11 (критично): смена семантики ATTR_SESSION / cookie-атрибутов ломает все тулы и SSO одновременно.
- SEC-1 (критично): `session.parameter.allow` → session fixation / утечка session id через Referer и логи.
- SEC-4 (критично): upload DoS; `upload.continueOverMax` может продолжить обработку после превышения.
- RN-2 (важно): int-константы session mode вместо enum — нет компиляторной проверки.
- RN-3 (важно): двойной парсинг multipart (RequestFilter + tool filter).
- RN-5 (важно): `@SuppressWarnings("deprecation")` на классе — scope неясен.
- RN-7 (важно): DiskFileItemFactory threshold=1024 → частые дисковые операции.
- RN-9 (важно): thread-local bindings без видимого TTL/eviction.
- RN-10 (важно): race на m_* если init() не завершён до первого запроса.
- RN-4 (важно, повышен из опционально по COVE): javadoc m_sakaiHttpSession описывает boolean, поле — int с 4 режимами.

- RN-11: версионировать cookie-контракт, вводить изменения через feature-flag с dual-read.
- SEC-1: запретить `session.parameter.allow` по умолчанию, требовать HTTPS + SameSite=Strict, ротация session id после аутентификации.

- RN-2: заменить int-константы на enum SessionMode с exhaustive switch + adapter.
- RN-3: проверять ATTR_UPLOADS_DONE перед повторным парсингом.

[REFACTORING]
Option A — Hardening in place (3–5 дней, риск низкий): try/finally cleanup, timeout+circuit breaker на ClusterService, запрет `session.parameter.allow`, принудительный HttpOnly+Secure+SameSite, abort при upload max. Минимальный blast radius, быстрый rollback.
Option B — Decompose into filter chain (10–15 дней, риск средний): EncodingFilter → UploadFilter → SessionFilter → PrincipalFilter → ClusterFilter → CookieFilter. SRP, тестируемость, enum SessionMode. Порядок фильтров критичен.
Option C — Facade + strategy (7–10 дней, риск средний-низкий): RequestFilter как фасад, стратегии SessionStrategy/UploadStrategy/ClusterStrategy/CookieStrategy. Инкрементальная миграция.
Рекомендация: A → C → B (сначала безопасность, потом архитектура).
