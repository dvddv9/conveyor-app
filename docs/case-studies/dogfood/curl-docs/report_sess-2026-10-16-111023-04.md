# curl CMake Build Documentation — Analysis (D3, spec)

[ECHO] Материал: `INSTALL-CMAKE.md` — процедурная спецификация сборки curl/libcurl через CMake. Охват: prerequisites → configure (cmake/ccmake/cmake-gui) → build → testing (не поддерживается) → install → consumer integration (find_package) → таблица опций. Slice обрывается на описании `CURL_CA_NATIVE`.

[ROUTE] stage4 → stage3 → stage5. task_type=spec → обязательны [MATRIX] + [INTERSECTION_RISKS]. [CHANGELOG] не применим (нет v1→v2).

[CONCLUSION] Документ покрывает happy-path сборки и даёт полную таблицу опций, но содержит критичное внутреннее противоречие (`BUILD_TESTING=ON` при явной неподдержке тестов) и молчаливые TLS-дефолты (`CURL_CA_BUNDLE=auto` без fallback). Пригоден для опытных пользователей; рискован для CI и downstream-дистрибутивов. Признаков подключения `config.yaml` к коду не обнаружено (VERIFY: не проверялось — материал является документацией).

[RISK_NODES]
- **RN-5 (критично):** `BUILD_TESTING=ON` по умолчанию при явном «The test suite does not yet work with the cmake build» → ложный сигнал готовности, падение `ctest` в CI.
- **SEC-1 (критично):** `CURL_CA_BUNDLE=auto` + `CURL_CA_FALLBACK=OFF` → молчаливый отказ HTTPS при отсутствии/подмене системного CA-бандла.
- **FP-1 (критично):** `cmake --install` с неверным `CMAKE_INSTALL_PREFIX` → необратимая перезапись системных файлов.
- **RN-1 (важно):** минимальная версия CMake не указана в тексте, отсылка к `CMakeLists.txt`.
- **RN-3 (важно):** сосуществование CMake / autotools / VS-решений без указания канонического пути.
- **RN-11 (важно):** `CMAKE_INSTALL_PREFIX` фиксируется на configure; `--prefix` молча игнорируется.
- **SEC-4 (важно):** отсутствие `CURL_PATCHSTAMP` → невозможность аудита security-версии.
- **RN-10 (опционально → VERIFY):** `SHARE_LIB_OBJECT=ON` на Windows при параллельных сборках — возможны гонки на объектных файлах.

[PLAN_B]
- RN-5: `BUILD_TESTING=OFF` по умолчанию до готовности тестов; при `ON` — явный warning.
- SEC-1: `CURL_CA_EMBED` для изолированных сборок; `CURL_CA_FALLBACK=ON` для остальных; post-install `curl -v https://example.com`.
- FP-1: `DESTDIR` для staged install; проверка префикса перед `cmake --install`.
- RN-1: явно указать min CMake version в тексте + `cmake --version` перед configure.
- RN-3: зафиксировать CMake как канонический для новых сборок; autotools — legacy; раздел миграции.
- RN-11: warning при `--prefix` + пример `cmake -B build -DCMAKE_INSTALL_PREFIX=/opt/curl`.
- SEC-4: обязательный `CURL_PATCHSTAMP` в CI-сборках.
- RN-10: одна build-директория = один процесс сборки; для параллельных — отдельные директории.

[THREAT_MODEL]
Trust boundaries: TB-1 (source → CMake), TB-2 (CMake → third-party TLS), TB-3 (artifacts → consumers), TB-4 (runtime → remote via CA), TB-5 (install → FS).
- **T (TB-1):** подмена `CMakeLists.txt`/`CURLConfig.cmake` → компиляция вредоносного кода. Критично.
- **S (TB-2):** подмена shared TLS-библиотеки через `LD_LIBRARY_PATH` → MITM. Критично.
- **T (TB-4):** `CURL_CA_BUNDLE=auto` без fallback → молчаливый отказ/подмена CA. Критично.
- **I (TB-3):** `CURL_HIDDEN_SYMBOLS=ON` + `VERSIONED_SYMBOLS=OFF` → ABI-утечка. Важно.
- **E (TB-5):** `cmake --install` с неверным префиксом → перезапись системных файлов. Важно.
- **R (TB-3):** отсутствие `CURL_PATCHSTAMP` → невозможность аудита. Важно.
- **S (TB-3):** `find_package(CURL)` без `COMPONENTS HTTPS` → приложение считает TLS доступным. Важно.
