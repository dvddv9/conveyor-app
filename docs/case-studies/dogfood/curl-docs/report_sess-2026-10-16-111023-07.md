# curl VERIFY.md — Анализ спецификации верификации релизов

[ECHO] Материал — политика/спецификация верификации релизов curl (VERIFY.md, ~150 строк). task_type=spec, level=D3, language=other. Анализ: подпись релизов (GPG), reproducible builds (Docker + scripts/verify-release), верификация исходников (git, CI, fuzzing, статические анализаторы). Кода/логов/инцидента нет.

[ROUTE] stage0 → stage4 (синтез) → stage3 (рефлексия) → stage5 (трансмиссия). research_first=false, parallel_stages=false, subst_count=0.

[CONCLUSION] Документ описывает многослойную supply-chain защиту curl (подпись + reproducible build + ревью + CI-контроли), уровень выше среднего для OSS. Однако trust anchor — один человек (release manager) и один keyserver; отсутствует threat model для компрометации ключа, provenance Docker-образа и процедура ротации/отзыва ключей. Reproducible build подаётся как гарантия безопасности, но доказывает лишь детерминизм. Признаков SBOM/SLSA/sigstore attestations в материале не найдено (VERIFY: не проверялось). Признаков процедуры действий при провале верификации не найдено (VERIFY: не проверялось).

[RISK_NODES]
- RN-1 (критично): неявное допущение — доверие к GPG-ключу с keyserver.ubuntu.com без независимой проверки; подмена ключа обходит всю цепочку.
- RN-2 (важно): слабое обобщение — reproducible build ≠ безопасность; вредоносный детерминированный код воспроизводится байт-в-байт.
- RN-3 (опционально): конкурирующая реализация — «напиши свой скрипт» без формального контракта верификатора (exit codes, формат OK).
- RN-4 (важно): сдвиг тезиса — «Do not trust, verify!» смещается к «trust our process»: большая часть списка — неверифицируемые декларации.
- RN-5 (важно): внутреннее противоречие — «we document everything» самореферентно; нет процедуры при провале верификации.
- RN-6 (критично): стратегическое избегание — обойдены компрометация ключа, ротация/отзыв, provenance Docker, SBOM/SLSA/sigstore.
- RN-7 (опционально): производительность — full verification тяжёл для CI; баланс стоимость/доверие не формализован.
- RN-8 (важно): надёжность — единая точка отказа: keyserver.ubuntu.com; Codeberg — backup git, не keyserver.
- RN-9 (опционально): масштабируемость — модель доверия к одному release manager не масштабируется; нет threshold signing.
- RN-10 (опционально): конкурентность — параллельные CI с общим Docker-кэшем могут давать недетерминизм (не адресовано).
- RN-11 (важно): ломающие изменения — «never breaking ABI/API», но формат verify-release и структура tarball не версионированы.

[INTERSECTION_RISKS]
- artifact (подпись) × build (Docker): оба зависят от одного release manager и одного образа → компрометация обходит оба слоя; ложное чувство многослойности.
- source (git) × infra (GitHub/2FA): компрометация GitHub-аккаунта с 2FA (session hijack) → внедрение кода, проходящего ревью.
- process (CI) × artifact (release): CI read-only, но reproducible build использует Docker вне CI-контроля → разрыв контроля.
- trust anchor (Daniel) × keyserver: коррелированный отказ — компрометация ключа и keyserver одновременно обнуляет цепочку доверия.

[ASSEMBLY] Слои: artifact (подпись tarball) → build (reproducible via Docker) → source (git review, style, banned functions) → process (CI, fuzzing, static analysis, torture tests) → infra (2FA, read-only CI, git backup, force-push ban). Сборка цепочки доверия линейна, но trust anchor — единая точка.

[REFACTORING] Рекомендуется: (1) разделить документ на верифицируемое/trust-based; (2) добавить формальный контракт verify-release; (3) добавить runbook при провале верификации; (4) пиннинг fingerprint и Docker digest; (5) threat model для release manager.

[PARALLELS] Аналогичные модели: Debian reproducible builds + signed releases; Tor Project (multiple signers); Rust (sigstore/cosign); SLSA framework. curl ближе к Debian-модели, но без threshold signing.

[TESTS]
Типы (заявлены): unit (тысячи), torture tests (инъекция отказов), fuzzing (OSS-Fuzz + CI), valgrind + sanitizers, static analysis (clang-tidy, CodeSonar, Coverity, Zeropath, Codex Security), CI (200+ jobs), zizmor на CI-конфигах.
Edge cases: провал подписи, провал reproducible build, dirty working tree, отсутствие git-репо (light mode), недоступность keyserver/docker.
Gaps: нет тестов самого процесса верификации (verify the verify — только рекомендация); нет тестов на компрометацию ключа/образа.
